## Critical source findings before implementation

### 1. Existing outcome evaluator is not sufficient

Current `evaluateSignalSnapshots` computes post-snapshot 1/3/5/10 returns and MFE/MAE from daily bars. It does not preserve Entry Zone/targets/invalidation, does not enforce target-after-entry ordering, and cannot truthfully resolve same-bar ordering. Therefore it must be **replaced inside the existing validation owner**, not supplemented by a second evaluator.

### 2. Replay requires a time-injected deterministic core

The current renderer `computePlan` reads global/current runtime context; `earningsInfo` depends on current wall-clock time, and Long-Term evaluation can consume current fundamentals. A historical replay cannot safely call this unchanged global path. The correct architecture is to refactor one deterministic core to accept an explicit context + `asOf`, while preserving the current live wrapper byte-for-behavior through the permanent **2403/2403** gate.

### 3. Present-day adjusted history can create replay lookahead

Canonical normal history uses provider-adjusted bars (`adjustment=all` when Alpaca is active), while corporate-action truth also retains raw comparison history when needed. A replay cutoff before a later split/action must not inherit a present-day adjustment decision silently. The existing corporate-action owner therefore needs cutoff-aware view semantics; creating a separate replay adjustment engine is prohibited.

### 4. Current history depth is not sufficient for all seasonality claims

The existing daily history window is optimized for live analysis and is typically around two years. Professional month-of-year seasonality needs deeper SPY/QQQ history to meet the new 8-year minimum. Extend the canonical history-depth policy selectively; do not create a seasonality database.

### 5. Arbitrary historical “exact replay” cannot be promised from data not retained

Current canonical state does not guarantee historical versions of every fundamental/news/SEC/macro/provider correction/settings value for arbitrary old dates. v16.3 must distinguish `EXACT` from `SCENARIO` replay and render `PARTIAL/UNAVAILABLE` when historical truth cannot be reconstructed.

## Implementation sequence derived from G2

1. **Refactor/freeze validation schema** first: immutable snapshot + evidence/version/levels/context fields, migration states.
2. **Refactor deterministic core for context/as-of injection** with 2403/2403 unchanged before adding replay orchestration.
3. **Build professional outcome evaluator** in the existing validation owner.
4. **Add cutoff-safe canonical historical view** via existing bar/corporate-action owners.
5. **Add isolated replay orchestration** with before/after state fingerprint tests.
6. **Add seasonality** over deeper routed SPY/QQQ canonical history.
7. **Add calibration** over completed outcome records only.
8. **Add correlation/concentration** over aligned canonical returns.
9. Integrate existing Research / Market Intelligence / Decision Queue / Maintenance / Documentation surfaces.
10. Run affected fast/functional/professional gates continuously; freeze immutable RC only after implementation closes.

## Components explicitly rejected by G2

- second deterministic engine;
- replay-specific scoring formulas;
- second bar/history database;
- second corporate-action adjustment pipeline;
- duplicate Evidence Snapshot;
- duplicate Market/Event Intelligence engine;
- validation-specific provider fetcher;
- new top-level Validation/Replay page;
- automatic “learned” changes to deterministic formula weights.

## G2 decision

**G2 REUSE / CONSOLIDATION / SOURCE-HEALTH AUDIT: PASS.**  
The architecture can support all five v16.3 requirements without duplicating canonical engines or stores. Production implementation should start with the validation-schema and deterministic-core refactors above.
