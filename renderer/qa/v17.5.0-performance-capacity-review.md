# DE.PULSE v17.5.0 — Performance / Capacity / Long-Run Closure Review

## Closure posture

v17 exists partly because runtime overload, intermittent degradation and slow response can become decision-support risk. Major Closure therefore requires measurable protection of critical evidence, not only faster code.

## Critical-path acceptance budgets

The canonical v17 SLO owner checks: Critical decision datasets; selected-symbol freshness; actionable-watchlist freshness; interactive API p95; provider queue depth/age; all bounded queues; persistence queue age; DB write rate; CPU utilization; local goroutine/heap budget; Opportunity Radar cycle; provider request budgets; live subscription utilization; warm-start coverage; canonical reuse/provider calls avoided; storage growth; and recovery telemetry.

Regular-session selected-symbol freshness is 100% current or BLOCK. Actionable-watchlist freshness targets at least 95% and BLOCKS below 80%. Interactive API p95 targets ≤250 ms and BLOCKS above 1000 ms. Provider queue target is depth <12 and age ≤2000 ms; depth ≥24 or age >5000 ms BLOCKS. CPU targets ≤70% and BLOCKS above 90%. Local process budget BLOCKS above 600 goroutines or 768 MiB heap. DB write rate targets ≤600 rows/min and BLOCKS above 3000 rows/min.

## Backpressure / load shedding

Tier 0/1 work is admitted ahead of broad/background work. Resource classes are bounded; queues are bounded; low-priority work sheds/rejects under pressure; provider request and subscription budgets remain observable. This is the central OPEN-003 architecture response.

## Persistence / warm start

SQLite persistence is asynchronous, material-change/coalescing driven and has observable queue/write/storage behavior. Warm-start telemetry reports target quotes, cache/persisted reuse and coverage. Persisted freshness labels are not trusted as timeless facts; current truth is re-derived.
