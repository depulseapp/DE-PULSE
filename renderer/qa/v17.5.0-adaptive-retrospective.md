# DE.PULSE v17.5.0 — Major-Version Adaptive Retrospective

## v17 outcome

v17 correctly evolved from “add a database” into a Persistent Intelligence + Runtime Load Resilience architecture. The most valuable improvements were not feature count: canonical reuse, truth-safe warm start, bounded workload/provider budgets, material-change propagation, reasoned degradation, measurable SLOs, and root-cause-preserving operational UX.

## What the build process caught

### RL-032 — Cross-platform persistence parity

The first v17.0 foundation was healthy on the primary host but Windows/CGO-disabled builds could silently select JSON rather than SQLite. Treating platform parity as blocking produced a real Windows SQLite backend via `winsqlite3.dll` instead of weakening the contract.

### RL-033 — Preserve root cause across downstream transformations

OPEN-002 was not only visual. A shared stale Quotes problem could become many symbol-level `LIQUIDITY RISK` cards. v17 now separates freshness/data-quality risk from current measured liquidity risk, while grouping repeated genuine causes and preserving every Review drill-down.

### RL-034 — Current build identity is not the same as latest Stable

Several inherited release/documentation gates encoded “current == v16.11 Stable.” During v17 TEST work that became a false failure. Governance now permits current TEST/RC identity while separately requiring v16.11 to remain the latest authoritative Stable until actual promotion.

### RL-035 — Consolidation includes deletion

The source-health gate prevented two forms of accumulation: duplicate Master Market Symbols render ownership and an obsolete liquidity wrapper left after refactoring. Tests were moved to canonical owners instead of whitelisting dead production code.

### RL-036 — Unique evidence ownership must shape the executable DAG

Major Closure exposed that pre-freeze still serialized historical scope gates that recursively reran evidence already owned by full-Go, renderer, deterministic and original-roadmap jobs. The DAG now uses static major-scope mapping plus each unique behavioral family once, reducing wrapper exposure without removing coverage.

### RL-037 — Predecessor Stable provenance is separate from candidate channel

The first v17.5 closure certification correctly retained the v16.11 Stable provenance anchors, but `v17_baseline_gate.py` still required the current candidate itself to be `TEST`. That rejected the legitimate RC lifecycle stage. The gate now protects the exact predecessor Stable SHA/fingerprint/GO anchors while permitting the current v17 family through TEST → RC before Stable promotion.

## Process performance

The sliced delivery model worked: v17.0 persistence foundation → v17.1 load/backpressure → v17.2 canonical intelligence/data efficiency → v17.3 measurable reliability → v17.4 UX/operational hardening → v17.5 Major Closure. It made defects attributable and allowed each slice to be source-qualified before the next depended on it.

Checkpointed race execution also proved useful. Wrapper/host interruptions were isolated from product failures, while direct race processes still had to pass the exact test partitions; no timeout was accepted as a product PASS without equivalent evidence.

## Keep for v18+

- Keep G0–G16 only; adapt existing gates rather than adding gate numbers.
- Keep current-build identity separate from latest Stable authority.
- Keep cross-platform capability parity explicit.
- Keep one canonical owner and delete superseded owners/helpers.
- Keep data-state root cause intact across downstream readiness/risk transformations.
- Keep heavy unique evidence as independent fingerprint-scoped jobs; do not recursively nest it in scope gates.
- Keep No Execution Boundary and `SHADOW → VALIDATED → APPROVED → PRODUCTION` governance.

## Retrospective verdict

**PASS.** Release Learning is extended through **RL-037** and each new lesson is attached to existing G0–G16 owners with durable regression protection. No new gate number is required.
