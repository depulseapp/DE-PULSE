# DE.PULSE v18.0.0 TEST — Principal Engineer Review

## Review posture

v18.0 is a separate TEST candidate built from the certified v17.5.1 Stable baseline. The review is limited to the Identity & Secure Session Foundation and inherited regression safety. v17.5.1 remains the authoritative Stable release; this review does not authorize Stable promotion or later v18 multi-user/provider work.

## Architecture ownership and reuse

- `Application.auth` remains the single HTTP authentication boundary; handlers do not create parallel authentication engines.
- `IdentityService` is the canonical owner for local user identity, password credential state, opaque server-side sessions, rotation, revocation, idle/absolute expiry, and principal resolution.
- The existing `PersistenceBackend` contract is extended with identity-state load/save rather than introducing a second database owner.
- v17 Provider Router, Global Symbol Registry, deterministic Day/Swing/Long engines, evidence/lineage owners, workload controller, and runtime priority tiers remain unchanged in authority.
- The v18 TEST profile is isolated as `PersonalMarketTerminal-v18-TEST`; first-run migration copies compatible v17 profile state without mutating the Stable profile.

## Credential and session security

- Local passwords use Argon2id only. The production profile is time=3, memory=64 MiB, parallelism=4, 16-byte random salt, and 32-byte derived key.
- Passwords are never persisted in plaintext. The persisted credential is a PHC-formatted Argon2id hash.
- Session cookies contain random opaque tokens; persistence stores only token hashes. Raw session tokens are not stored.
- Session rotation invalidates the predecessor. Password establishment/change revokes prior sessions and rotates to a fresh session.
- Idle and absolute expiry are independently enforced. Lifetimes are centralized so v18.2 can later expose controlled policy without scattered constants.
- Argon2id verification runs outside the identity-state mutex and the user/hash/status state is revalidated before session issuance, preventing password hashing from serializing unrelated session resolution.

## HTTP authorization and request integrity

- Secure-session cookie shaping is HttpOnly + SameSite=Strict; `Secure` is enabled when TLS is in use.
- State-changing authenticated requests require the double-submit CSRF value in `X-DE-PULSE-CSRF`.
- Bootstrap OWNER compatibility is intentionally narrow: the one-time bootstrap session may set the first password or sign out, while normal application APIs return HTTP 428 until the credential is established.
- Shared/system maintenance and configuration mutations are ADMIN-or-higher; ordinary USER principals are denied by centralized role policy.
- Login remains a pre-authentication endpoint; logout and password mutation require authenticated CSRF protection.

## Persistence and migration safety

- SQLite schema v3 adds v18 identity state without rewriting v17 market/evidence tables.
- Native SQLite remains the desktop persistence path where available; the existing CGO-disabled fallback retains the same identity security property and is regression-tested.
- Windows x64 cross-compilation succeeds against the Windows persistence implementation.
- First v18 TEST launch clones compatible settings/watchlists/API-key/profile state into a separate TEST profile and excludes instance/log runtime artifacts. Stable is never overwritten by this migration path.

## Residual risk / later scope

- v18.0 deliberately implements the local OWNER credential/session foundation, not full v18.1 per-user symbol ownership or v18.2 user administration/presence policy.
- Brute-force/rate-limit hardening, broader penetration testing, hosted TLS termination assumptions, commercial/data-rights hardening, and emergency multi-user session operations remain later committed v18 scope.
- Native macOS packaging with SQLite must be built and audited on a compatible macOS release host; a Linux cross-build with CGO disabled must not be presented as equivalent native macOS SQLite evidence.
- Live-provider entitlement/network acceptance remains environment-dependent and must continue to degrade truthfully.

This is not a Stable promotion. v17.5.1 remains authoritative Stable until a later release process explicitly replaces it. Smart Provider Router v2 may begin only after v18.0 TEST foundation qualification is closed according to the controlling handoff.
