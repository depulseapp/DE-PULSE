## Version/build delivery rule

Public planning and delivery are version-oriented. Requirement IDs, audit rows, backlog acceptance bullets, commits and CI evidence remain granular inside the version but do not become separate release packets.

For each version:
- use one coherent development branch/PR unless governance explicitly requires otherwise;
- a canonical Fast exact-head PASS is required for the coherent candidate;
- a Qualified exact-head PASS is required at G10 and other material risk boundaries selected by Impact Planner/current governance;
- Release G11-G16 is used only for a release candidate;
- batch related small changes when they share owners/evidence;
- split genuinely heavy/high-risk features into real patch versions rather than hidden pseudo-releases;
- cancel/supersede obsolete candidate runs when supported, but never reuse evidence from the wrong head;
- keep the three canonical workflow families: Fast, Qualified, Release;
- no 5/5 maturity claim from prose or stale evidence.

## Compatibility-first delivery rule

Architecture migration delivery must prove:

`CHARACTERIZE -> NEW OWNER PRESENT -> DUAL/SHADOW COMPARISON -> CONSUMER MIGRATION -> PARITY/IMPROVEMENT -> OLD AUTHORITY RETIRED -> REGRESSION RETAINED`

A migration is not delivered merely because the new path works. Evidence must prove affected existing clients/capabilities are not silently lost. This applies to renderer scoring, RuntimeSnapshot, Radar/Discovery lifecycle, Watchlists/workspaces, full-snapshot SSE, provider direct paths, auth/session and persistence schema.

Golden vectors must distinguish intentional defect corrections from accidental behavior drift.

## Cross-platform delivery

Shared capability is not complete until every REQUIRED client is equivalent in meaning. Mac/Windows/Web may differ in platform mechanics, not domain truth, auth/role semantics, provider rights, freshness/provenance, intelligence conclusions or durable state.

Core owns data acquisition, secrets/rights, canonical state, deterministic intelligence, opportunity/briefs, outcomes/adaptive jobs, tenant persistence/recovery/audit and AI gateway policy. Clients own interaction/rendering/charts/accessibility and typed API/event validation. Desktop may keep encrypted authorized last-known cache and OS notification/deep-link behavior; it must never present stale cache as live confidence.

Distribution maturity requires, when targeted:
- macOS Developer ID + hardened runtime + notarization + stapling;
- Windows trusted signing + installer/update strategy;
- secure OS credential storage;
- signed update manifests, staged channels and rollback;
- minimum-client/deprecation/forced-upgrade compatibility rules;
- crash/support diagnostics with redaction.

## Adaptive/AI delivery

Adaptive influence progresses through point-in-time outcome evidence, registered challenger, shadow inference, drift/subgroup evaluation, sample/metric gates, explicit approval, gradual production and rollback thresholds. SHADOW cannot silently become production.

AI/agent/MCP changes preserve canonical market-data owners, rights filtering, provenance, audit and deterministic non-AI operation. Prompt-injection resistance and source isolation require adversarial evals; structured schema success is not factual correctness.

## Commercial/public delivery boundary

Technical 5/5 readiness can include provider-rights evidence, signed installers, update/rollback, privacy, billing/support and operational readiness. It still does not activate public/commercial use. Activation requires a separate explicit Owner decision and dedicated activation audit.

No development key/broker/data account is assumed to authorize display to unrelated paying users. Contractual rights remain external evidence.

## Scale / operations delivery

Before service commitments, evidence must match expected scale:
- around 100 users: rights, user-scoped deltas, managed secrets, signed beta channel and support runbooks;
- around 1,000 users: shared ingestion, normalized tenant DB, outbox/workers, rate/cost budgets and durable alert fanout;
- around 10,000 users: partition/retention, queue ownership, quotas, SLO/error budgets, unbiased adaptive sampling and on-call capacity.

Do not introduce Kafka/Kubernetes because a future user count sounds large. Postgres + outbox + stateless API/workers remains the default until measured throughput/replay/independent scaling/team ownership proves extraction value.

## CI efficiency without quality loss

CI savings come from coherent candidate batching, dependency-aware Impact Planner routing, frozen v18 evidence when unchanged and risk-targeted native/browser/release lanes. Do not remove assurance to meet a budget.

Provider tests use deterministic fixtures/historical replay/canonical cached evidence for normal CI; bounded live smoke is used only when auth/entitlement/real transport/effective capability is the subject.
