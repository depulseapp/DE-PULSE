# DECISION — v18.9 → v20 Dependency-First Release Train

**Status:** APPROVED GOVERNANCE ALIGNMENT / DRAFT PR #67 UNTIL MERGED  
**Date:** 2026-08-21  
**Affects:** canonical Roadmap, Current Adaptive Roadmap, Build Plan, Build Process, Delivery Process, persistence/readiness contract, handoff, issue #65 and issue #66  
**Does not authorize:** any v19 product implementation before ordered v18.9.x closure

## Context

A cross-contract audit found three sequencing problems:

1. provider observability/Adaptive telemetry was scheduled after most TradeInsight SHADOW capability expansion, making usefulness/promotion evidence arrive too late;
2. issue #66 hosted account/sync work was represented as both a large standalone program and another v19 packet, creating ambiguous dependency order;
3. the canonical Roadmap still contained historical provisional `v18.3 PostgreSQL / v18.4 hosted-security` placement even though the current certified v18.9 product and handoff defer hosted PostgreSQL/multi-device synchronization to v19+.

The audit also found that model/prompt governance should precede broad v20 adaptive rollout rather than appear late in the adaptive program.

## Decision

Adopt this permanent sequencing principle:

`stabilize -> canonicalize -> instrument -> validate -> expand -> harden -> close -> control plane -> hosted data plane -> platform parity -> evidence substrate -> reliability/readiness -> adaptive control/governance -> adaptive intelligence`

### v18.9.x alignment

Keep `v18.9.1` crash-only scope unchanged. Move provider observability/Adaptive telemetry to `v18.9.6`, before TradeInsight capability expansion:

- `v18.9.1` runtime crash
- `v18.9.2` TradeInsight Settings/API-key UX
- `v18.9.3` coverage-aware persistence-first Smart Provider Router
- `v18.9.4` canonical company/instrument identity
- `v18.9.5` Market Data Modes/capability diagnostics
- `v18.9.6` provider observability/Adaptive telemetry
- `v18.9.7` TradeInsight Form 4 SHADOW enrichment
- `v18.9.8` TradeInsight symbol/company search
- `v18.9.9` TradeInsight movers/ranking SHADOW evidence
- `v18.9.10` remaining useful capability admission
- `v18.9.11` Session-Aware Data Readiness Maintenance
- `v18.9.12` professional closure

### v19 version bands

Use minor bands as coherent dependency phases while keeping each patch one primary responsibility:

- `v19.0.x` — rights/identity/PostgreSQL/secrets/SLO/data-quality control-plane foundation
- `v19.1.x` — zero-key Hosted Provider Gateway + entitlement-safe live serving + sync protocol + macOS pilot/desks
- `v19.2.x` — Windows/web/research parity + multi-user hardening + #66 adversarial closure
- `v19.3.x` — point-in-time 13F/TDTI/AODR evidence substrate
- `v19.4.x` — ADR-GDI professional reliability/economics + paid-provider gap evaluation + v20 readiness
- `v19.5.0` — no-feature Major Closure

### v20 version bands

Move model/prompt governance to the control phase before broad adaptive feature rollout:

- `v20.0.x` — experiment ledger, model/prompt governance, analogues and calibration/drift
- `v20.1.x` — ASBI
- `v20.2.x` — adaptive Institutional/13F + TDTI
- `v20.3.x` — AODR
- `v20.4.x` — ADR-GDI adaptive operations
- `v20.5.0` — no-feature Professional Closure

## Version semantics

- Major = strategic maturity generation.
- Minor band = coherent platform phase/dependency layer.
- Patch = one primary independently certifiable responsibility.
- Future labels are planned reservations until G1.
- G0/G1 may split broad work and shift later unstarted reservations inside a band.
- Shipped versions are immutable and are never renumbered.
- Corrective/security releases may preempt the planned train.

## Hosted architecture placement correction

Historical roadmap labels that provisionally placed PostgreSQL/hosted state in earlier v18 minors are superseded as **future placement only**. They are not retroactively claimed as implemented.

Current authoritative direction:

`v18.9.x native-first closure -> v19.0 hosted control-plane foundations -> v19.1 hosted Provider Gateway/sync -> v19.2 cross-platform parity/assurance`

SQLite remains native edge/offline state; PostgreSQL becomes shared hosted authority only when the v19 foundation is implemented. Normal commercial users remain zero-key and access providers only through DE.PULSE server-side credentials/rights enforcement.

## Industry-strength controls inside existing G0–G16

No G17+ is created. Hosted/security/data/adaptive work strengthens existing gates with:
- architecture decision/trust/data classification and threat-model scope;
- API/schema/protocol compatibility;
- expand/contract migration and rollback/roll-forward planning;
- SLO/error-budget and observability before broad activation;
- negative authorization/tenant/rights/secret testing;
- load/soak/capacity/failure-injection/failover/backpressure evidence;
- feature flags/kill switches/canary or bounded activation where useful;
- direct-route/API/SSE authorization consistency;
- production-readiness blocking on unresolved P0 security/rights/recovery/compatibility defects;
- implementation-miss/incident/metric learning at G16.

## Supersession / continuity

This decision supersedes only obsolete **future version placement** that conflicts with the certified v18.9 source of truth. It does not delete or invalidate durable approved product workstreams. Historical requirements remain traceable through their original decisions, scope files, release evidence and recovery programs.
