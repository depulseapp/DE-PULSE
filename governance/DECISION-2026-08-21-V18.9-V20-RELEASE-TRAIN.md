# DECISION — v18.9 → v20 Dependency-First Release Train

**Status:** APPROVED GOVERNANCE ALIGNMENT / DRAFT PR #67 UNTIL MERGED  
**Date:** 2026-08-21  
**Affects:** canonical Roadmap, Current Adaptive Roadmap, Build Plan, Build Process, Delivery Process, persistence/readiness contract, handoff, issue #65 and issue #66  
**Does not authorize:** any v19 product implementation before ordered v18.9.x closure

## Context

A cross-contract audit found six sequencing/authority problems:

1. provider observability/Adaptive telemetry was scheduled after most TradeInsight SHADOW expansion, so usefulness/promotion evidence arrived too late;
2. issue #66 hosted account/sync work appeared both as a large standalone block and another v19 packet, creating ambiguous dependency order;
3. the canonical Roadmap retained historical provisional `v18.3 PostgreSQL / v18.4 hosted-security` placement even though certified/current v18.9 truth defers hosted PostgreSQL/multi-device synchronization to v19+;
4. hosted authorization concepts risked being conflated: tenant identity, RBAC, DE.PULSE subscription/product entitlement and upstream provider legal/data rights are related but semantically different controls;
5. account-data/privacy lifecycle was only implicit, leaving export/deletion/retention/backup/residency/operator-access behavior at risk of being retrofitted after hosted schema decisions;
6. hosted environment/IaC and software-supply-chain assurance were gate-level expectations but not first-class release responsibilities, leaving production environment drift and artifact/dependency provenance under-specified.

The audit also found that model/prompt governance should precede broad v20 adaptive rollout rather than arrive late.

## Decision

Adopt this dependency-first sequencing principle:

`stabilize -> canonicalize -> instrument -> validate -> expand -> operationalize -> close -> establish tenant/security/rights/product-entitlement/privacy control plane -> establish hosted environment/IaC trust -> establish recoverable persistence/secrets -> establish software-supply-chain provenance -> activate provider data plane -> synchronize -> prove platform parity -> harden multi-user operation -> build point-in-time evidence -> prove reliability/readiness -> govern models -> expand adaptive intelligence`

## Hosted serving model — separate dimensions

Never represent these as one generic `entitled=true` concept:

1. **Tenant/account identity** — ownership/isolation of request and persisted state.
2. **RBAC/capability authorization** — what a user/device/session may do.
3. **DE.PULSE product entitlement** — what the customer's DE.PULSE plan/status/quota permits the product to expose.
4. **Provider legal/data rights** — what upstream contracts permit DE.PULSE to acquire/cache/retain/derive/display/redistribute.
5. **Privacy/data-governance policy** — what account/user/device data may be retained, exported, deleted, observed by operators, and where it may reside.

Hosted reads, writes, cache reuse, persistence and stream projections apply the relevant dimensions independently. Billing-provider integration may be deferred for internal pilot, but product-entitlement enforcement and privacy/data-lifecycle policy must exist before external commercial multi-user activation.

## Version semantics

- Major = strategic maturity generation.
- Minor band = coherent dependency phase.
- Patch = one primary independently certifiable responsibility.
- Future labels are planned reservations until G1.
- G0/G1 may split broad work and shift later unstarted reservations inside a band.
- Shipped versions are immutable and never renumbered.
- Corrective/security releases may preempt the planned train.

## Hosted architecture placement correction

Historical roadmap labels that provisionally placed PostgreSQL/hosted state in earlier v18 minors are superseded as **future placement only**. They are not retroactively claimed as implemented.

Current direction:

`v18.9.x native-first closure -> v19.0 tenant/rights/product-entitlement/privacy/environment/persistence/secrets/supply-chain control plane -> v19.1 zero-key Provider Gateway/sync -> v19.2 cross-platform parity/assurance`
