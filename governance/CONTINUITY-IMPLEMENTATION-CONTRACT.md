# DE.PULSE — 10/10 Continuity & Governance-to-Implementation Contract

**Status:** PERMANENT / CANONICAL CARRY-FORWARD CONTRACT  
**Effective:** 2026-08-14  
**Applies to:** all approved DE.PULSE scope, roadmap, build plans, release gates, delivery, documentation, historical Stable guarantees, and future adaptive learning  
**Classification:** REFINEMENT / HARDENING + reconciliation of previously approved/certified direction; no duplicate product architecture is created by this contract.

---

## 1. Purpose

DE.PULSE must not lose product truth simply because a decision originated in an older release handoff, Stable certification record, prior Adaptive Roadmap, recent discussion, or an active development branch rather than the newest condensed governance files.

The permanent closure chain is:

**DISCUSSED → EXPLICITLY APPROVED → CANONICALIZED → ROADMAP-PLACED → G1-FROZEN WHEN APPLICABLE → IMPLEMENTED → ENFORCED → EVIDENCED → PACKAGED/RUNTIME-PROVEN → DELIVERED → OUTCOME-MEASURED → LEARNED → ADAPTED**

A document never proves implementation. Equally, absence from a newer summary document must never silently delete an already approved or certified capability.

Permanent rule:

> **Governed → Implemented → Enforced → Evidenced → Delivered → Learned.**

Every approved requirement must be either implemented/evidenced in the release where it applies or explicitly classified and carried to a named future release. `Documented but forgotten` is not an allowed state.

---

## 2. Canonical Continuity Rule

When reconciling old and new truth, use:

1. actual source / certified packaged-runtime evidence for what really existed;
2. current canonical governance for approved intent;
3. historical immutable Stable release evidence for inherited implemented capability;
4. current release G1 for the frozen release slice;
5. active development evidence for work not yet merged to Stable;
6. decision history and handoffs for provenance/context.

If an older certified capability is missing from a condensed current governance summary, classify it before any deletion or behavioral removal:

- **PRESERVE / INHERITED STABLE TRUTH**;
- **CONSOLIDATE / SAME CANONICAL OWNER**;
- **SUPERSEDED WITH APPROVED REPLACEMENT**;
- **INTENTIONALLY RETIRED WITH EVIDENCE**;
- **UNKNOWN / RECONCILE BEFORE CHANGE**.

No feature, boundary, defect, test guarantee, provider/data rule, UI contract, or release obligation may disappear because a handoff or newer file omitted its wording.

# 3. Reconciled Permanent Product / Intelligence Truth

The following items are explicitly carried forward as permanent approved DE.PULSE truth. They reuse existing canonical owners and do not create parallel engines.

## CONT-001 — U.S. Equities Processing Boundary

Actionable per-symbol processing is for **U.S.-listed stocks and approved U.S.-listed ETFs/securities** under the Reliable Actionable Universe and Global Symbol Registry.

Global market, macro, FX, commodity, rates, geopolitical and other non-U.S. evidence may be used selectively as **context for U.S. equity decisions** when useful, fresh, lawful and material.

Do not silently broaden actionable per-symbol processing into foreign-equity execution/recommendation scope merely because reference/context data exists.

U.S.-listed foreign-origin companies remain eligible when they satisfy the U.S. listing and reliability rules.

## CONT-002 — U.S.-Primary Economic Calendar / Event Semantics

Economic/Event Intelligence remains U.S.-decision-centric and uses the existing Event Intelligence / Macro ownership rather than creating another calendar engine.

Preserve semantic classes equivalent to:

- **US_MARKET_CRITICAL** — material U.S. events capable of affecting U.S. market readiness/Event Mode;
- **US_CONTEXT** — useful U.S. context that is not independently critical;
- **GLOBAL_CONTEXT** — material foreign/global context relevant to U.S. decisions.

A foreign event must not automatically trigger full U.S. market-critical behavior merely because it is globally important. Materiality, relevance, timing and actual market impact must govern escalation.

## CONT-003 — Community Intelligence / Global Evidence Fusion Hub

Preserve one canonical, source-agnostic **Global Evidence Fusion Hub** for permitted community/social evidence rather than separate social-feed products.

Canonical flow:

**source → rights/AI eligibility → normalize → U.S. ticker/entity resolution → deduplicate/repost cluster → spam/noise filtering → mention velocity/source diversity/narrative change → authoritative corroboration → materiality/confidence → canonical evidence event → authorized consumers**

Potential adapters include permitted/official/user-authorized X, Reddit, Discord, Telegram and future sanctioned WhatsApp or equivalent sources.

Community evidence is explicitly contextual/untrusted until corroborated as appropriate and cannot directly mutate protected deterministic Day/Swing/Long truth.

Telegram/Watcher Guru or similar fast-alert context may be used in private development only within applicable terms; prefer resolving/corroborating the underlying event from authoritative sources before durable/AI use. Commercial/hosted readiness requires rights review and source replacement/restriction/removal where needed.

## CONT-004 — Unusual Volume & Volatility Intelligence

Preserve the already-established Unusual Volume & Volatility capability as part of **Opportunity Radar / Discovery**, not a duplicate scanner.

Applicable qualification includes:

- session/time-of-day-normalized relative volume;
- dollar-volume and liquidity/spread gates;
- range/volatility expansion;
- price dislocation and confirmation;
- persistence across Radar cycles;
- catalyst/news/event context;
- permitted fused community context as supporting evidence only;
- provider/data-health truth.

Its Opportunity/Discovery score is contextual discovery intelligence, not a protected Day/Swing/Long score and not a probability-of-profit promise.

Promotion/demotion remains bounded, hysteresis/TTL-aware, provider-budget-aware and respectful of active-user/watchlist priority. `SPY`/`QQQ` remain market-critical context and `GLD`/`SLV`/`USO` remain approved high-priority actionable tradable exceptions.

## CONT-005 — Historical Replay / Point-in-Time Validation Preservation

Historical Replay/Scenario validation remains a real validation/learning capability using actual canonical evidence and deterministic engines with strict no-lookahead truth.

It is not paper trading, mock brokerage or an execution simulator.

Future ASBI/TDTI/AODR/13F/adaptive evaluation must build on point-in-time history rather than bypassing this truth contract.

# 4. Ownership, Administration & Transferability

## CONT-006 — Canonical Ownership Role Model

Preserve the approved ownership hierarchy:

- exactly **1 active SUPER OWNER** at all times;
- up to **5 active OWNER** accounts in addition;
- ADMIN / USER / DEMO below them.

SUPER OWNER-only irreversible ownership authority includes applicable:

- transfer/sale of DE.PULSE ownership;
- appointment/removal of OWNERs;
- controlled successor SUPER OWNER promotion/transfer;
- other irreversible ownership-authority actions.

OWNER retains full ordinary product/platform governance and proprietary documentation access but cannot create/replace/demote the SUPER OWNER or independently transfer ownership.

ADMIN authority is **capability-based**, not inferred merely from the ADMIN label. Limited ADMIN receives only explicitly delegated capabilities; selected/full-capability ADMIN may receive deeper operational rights only through the canonical authorization owner.

UI visibility, direct-route access, APIs, payload redaction and audit evidence must consume the same authorization truth.

## CONT-007 — Transferable Asset Registry / Ownership Transfer Readiness

DE.PULSE must remain transferable as a coherent product asset rather than depending on undocumented personal knowledge.

Maintain a governed **Transferable Asset Registry** covering applicable:

- official system identity/email;
- market-data subscriptions and provider/service accounts;
- API credentials/key ownership metadata without exposing secrets in docs;
- billing ownership;
- recovery/MFA ownership;
- domains/certificates;
- cloud/server/hosting assets;
- source repository/release/signing ownership;
- build/release infrastructure;
- documentation/governance;
- audit/history/provenance;
- data-rights/licensing obligations;
- dependencies and transfer prerequisites.

Actual secret material must remain protected; the registry records ownership, location/process and transfer responsibility rather than leaking credentials.

Ownership transfer requires reauthentication, explicit audit evidence, successor validation and rollback/recovery planning appropriate to the action's risk.

# 5. Role-Aware Documentation & AI Retrieval

## CONT-008 — Documentation Classes / RBAC

Preserve role-aware in-product documentation:

- **USER** — sanitized usage/workflow/freshness/readiness documentation;
- **DEMO** — limited Quick Start/help appropriate to demo access;
- **ADMIN** — user docs plus only authorized operational/admin documentation;
- **OWNER / SUPER OWNER** — full proprietary developer/product-engineering/governance documentation.

Selected ADMIN capability delegation may expose deeper operational documentation only when the same backend authorization allows the underlying capability.

Server-side authorization is mandatory; hiding a tab is not access control.

AI/retrieval must inherit the same document-level/capability-level authorization. Do **not** retrieve privileged OWNER content and rely on prompt instructions to suppress it afterward.

Each canonical documentation module should maintain useful metadata such as document ID, audience, owner, introduced version, last-updated version, related contract, dependencies, status and integrity/hash where appropriate.

Builds should update only materially impacted documentation modules and produce/maintain a Documentation Impact Manifest or equivalent traceability. Stale or role-leaking documentation can fail release qualification.

# 7. Executable Governance Closure

## CONT-010 — Governance Is Executable Product Intent

All permanent approved governance—not only this contract—must have an implementation disposition.

Every material governance item is classified as one of:

- **CURRENT_RELEASE_BLOCKER** — must be implemented/evidenced before the current release can freeze/promote;
- **CURRENT_RELEASE_PROCESS_HARDENING** — build/release machinery required for trustworthy evidence and must close before the affected gate is PASS;
- **NEXT_RELEASE_MANDATORY_ENTRY** — source-changing work discovered after current G1 that must enter the named next release at G1–G3 and cannot become optional backlog;
- **FUTURE_STRATEGIC** — deliberately deferred direction with explicit target/review point;
- **ALREADY_IMPLEMENTED / INHERITED** — proven existing behavior that remains a protected regression contract;
- **OPEN_DEFECT / RECONCILE** — observed issue that remains open until closure evidence exists.

`APPROVED` is never a synonym for `IMPLEMENTED`.

## CONT-011 — Required Traceability Chain

For applicable scope, maintain traceability:

**Approved Scope / Contract ID → roadmap placement → release disposition → G1 item → canonical owner → implementation/source → automated tests/gates → packaged-runtime evidence → Stable disposition → outcome/telemetry → G16 learning**

At G10/G12/G14/G16, explicitly detect:

- approved but never scheduled;
- scheduled but never implemented;
- implemented but not integrated;
- integrated but not tested;
- tested source but not packaged/runtime-proven;
- runtime-proven but ineffective/noisy/low-value;
- useful and worth strengthening;
- redundant/obsolete and safe to consolidate or supersede.

A release cannot mark a governance item PASS because its documentation is correct while the actual source/runtime contradicts it.

# 10. Open Defect Carry-Forward — No False Closure

## CONT-021 — Master Market Symbols Control/Layout

Status: **OPEN_DEFECT / RECONCILE** until actual current source/runtime evidence proves closure.

Requirements:

- preserve canonical Global/Master Symbol Registry behavior;
- fix layout/control hierarchy without changing symbol semantics accidentally;
- validate responsive geometry and add/remove behavior;
- preserve idempotency/no duplicate membership effects;
- do not mark closed from an old plan or screenshot alone.

## CONT-022 — Prep `Requires Review` Repetition / Information Hierarchy

Status: **OPEN_DEFECT / RECONCILE** until current runtime evidence proves closure.

Observed risk: Pre-Market/Market Open Prep may show a long vertical list of repeated per-symbol warnings (for example repeated liquidity-risk cards), burying material exceptions and potentially exaggerating one upstream problem as many independent problems.

Required behavior when backend truth is correct:

- surface shared/root cause once where applicable;
- group by reason/severity;
- show counts;
- sort by severity/materiality/actionability;
- bound the initial list;
- provide View All/collapsible drill-down;
- preserve per-symbol details when expanded;
- deduplicate identical reason text;
- never hide genuinely independent material risk.

If repetition reflects a shared stale/degraded upstream dependency, ADR-GDI blast-radius/reason semantics should explain that cause rather than presenting it as unrelated symbol failures.

# 12. Branch / Governance Synchronization Rule

## CONT-024 — Preserve Both Canonical Governance and Unique Active Implementation

When `main` governance advances while an active development branch contains unique implementation work, integration must preserve **both** sets of truth.

Do not restart/rebase away unique implementation merely to obtain a visually clean history. Before release qualification:

1. identify the exact merge base and branch heads;
2. enumerate governance-only changes and unique implementation changes;
3. reconcile conflicts by canonical ownership/approved intent, not by newest timestamp alone;
4. preserve active release G1 immutability unless an approved scope-change mechanism applies;
5. bring future-release governance into the branch as inherited/future truth without falsely declaring it implemented in the current frozen release;
6. rerun affected tests/evidence after integration;
7. prove no unique implementation or canonical governance requirement was dropped.

# 13. G0–G16 Integration

This contract creates **no new gates**.

- **G0:** load current governance + this contract + previous Stable traceability + active branch/open defects; detect omissions/divergence.
- **G1:** classify every applicable obligation as blocker/process-hardening/next-release/future/inherited/open-defect; freeze current release slice.
- **G2:** enforce canonical owner and REUSE → CONSOLIDATE → REFACTOR → DELETE/REPLACE → ADD.
- **G3:** define dependencies, rights, role matrix, platform matrix, test oracle and closure evidence.
- **G4:** implementation must actually exist for current blockers.
- **G5/G6:** prove fast regression and cross-module integration without duplicate owners.
- **G7:** prove data/security/RBAC/AI retrieval/point-in-time/rights truth.
- **G8:** prove performance/provider/DB/load behavior and no self-inflicted degradation.
- **G9:** prove role-aware UI/UX, responsive composition, information hierarchy and open-defect closure where claimed.
- **G10:** run Approved Scope + Continuity Traceability before freeze; documented-only is not PASS.
- **G11/G12:** freeze/certify the exact reconciled candidate.
- **G13:** build required platform artifacts from the exact certified source.
- **G14:** verify actual packaged/runtime behavior and required platform evidence.
- **G15:** confirm provenance, rollback, promotion truth and no silent omission.
- **G16:** reconcile every approved/governed item to implemented/deferred/open/superseded status; update roadmap/governance; clean obsolete branches/workflows/docs only after preservation proof.

# 14. 10/10 Continuity Quality Scorecard

A continuity/governance reconciliation may be called **10/10** only when all ten dimensions pass:

1. **Discussion/Approval Coverage** — material approved items in the review window are accounted for.
2. **Historical Stable Coverage** — relevant certified inherited capabilities are accounted for.
3. **Canonical Ownership** — no duplicate engines/routers/stores were introduced by reconciliation.
4. **Roadmap/Release Disposition** — every non-current item has a named placement/classification.
5. **Executable Traceability** — requirement → owner → source → tests → package/runtime → G16 path exists where applicable.
6. **Defect Continuity** — unresolved user-reported defects remain explicitly open until evidence closes them.
7. **Security/Rights/Role Continuity** — RBAC, data rights, AI retrieval and ownership-transfer boundaries survive UI/docs refactors.
8. **Performance/Reliability Continuity** — inherited features remain bounded, provider-efficient and ADR-GDI-compatible.
9. **Delivery/Platform Truth** — required native/hosted targets and actual-artifact proof are explicit; no fabricated platform PASS.
10. **Future-Loss Prevention** — G0/G10/G16/Major Closure can detect approved-but-missing, implemented-but-unintegrated and silently dropped capabilities.

A score below 10 requires remediation before describing the reconciliation itself as 10/10.

This score is **governance-continuity quality**, not a claim that every future ASBI/TDTI/AODR/ADR-GDI feature is already implemented in the current app.

# 15. Adaptive Use — Not Shelfware

The purpose of this contract is to change build behavior, not accumulate documents.

Future build planning must actively consume these requirements. G16 must measure whether governed capabilities were actually useful, reliable, efficient and understandable, then:

**preserve what works → strengthen what adds decision value → consolidate duplication → fix failure modes → retire low-value/redundant behavior with evidence → feed the next adaptive plan**.

DE.PULSE should become simpler to use while becoming more capable internally. Governance exists to make that evolution safe, traceable and cumulative—not to freeze the product or create paperwork.
