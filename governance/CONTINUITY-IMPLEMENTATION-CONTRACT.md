# DE.PULSE — 10/10 Continuity & Governance-to-Implementation Contract

**Status:** PERMANENT / CANONICAL CARRY-FORWARD CONTRACT  
**Effective:** 2026-08-14  
**Applies to:** all approved DE.PULSE scope, roadmap, build plans, release gates, delivery, documentation, historical Stable guarantees, active development, unresolved defects and future adaptive learning  
**Classification:** REFINEMENT / HARDENING + reconciliation of previously approved/certified direction. This contract creates no duplicate product architecture and no G17+ gate.

---

# 1. Purpose

DE.PULSE must not lose product truth because a decision originated in an older release handoff, Stable certification record, prior Adaptive Roadmap, recent discussion, or an active development branch rather than the newest condensed governance files.

Permanent lifecycle:

**DISCUSSED → EXPLICITLY APPROVED → CANONICALIZED → ROADMAP / RELEASE DISPOSITION → G1-FROZEN WHEN APPLICABLE → IMPLEMENTED → ENFORCED → EVIDENCED → PACKAGED/RUNTIME-PROVEN → DELIVERED → OUTCOME-MEASURED → LEARNED → ADAPTED**

A document never proves implementation. Absence from a newer summary never silently deletes approved/certified behavior.

Permanent closure rule:

> **Governed → Implemented → Enforced → Evidenced → Delivered → Learned.**

`Documented but forgotten` and `approved therefore implemented` are forbidden states.

# 2. Canonical Continuity / Reconciliation Rule

When old and new truth differ or appear incomplete, use:

1. actual source and certified packaged-runtime evidence for what really existed;
2. current canonical governance for approved intent;
3. this carry-forward contract for reconciled older approved/certified truth and implementation obligations;
4. historical immutable Stable traceability/Major Closure evidence for inherited implementation;
5. current release G1 for the frozen release slice;
6. active development evidence for work not yet promoted;
7. Decision Log/handoffs for provenance and context.

Before deleting or materially changing an older capability, classify it:

- **PRESERVE / INHERITED STABLE TRUTH**;
- **CONSOLIDATE / SAME CANONICAL OWNER**;
- **SUPERSEDED WITH APPROVED REPLACEMENT**;
- **INTENTIONALLY RETIRED WITH EVIDENCE**;
- **UNKNOWN / RECONCILE BEFORE CHANGE**.

No feature, boundary, defect, test guarantee, provider/data rule, UI contract or release obligation may disappear merely because newer documents condensed the wording.

# 3. Reconciled Permanent Market / Intelligence Truth

## CONT-001 — U.S. Equities Processing Boundary

Actionable per-symbol processing is for **U.S.-listed stocks and approved U.S.-listed ETFs/securities** under Global Symbol Registry + Reliable Actionable Universe truth.

Global market/macro/FX/commodity/rates/geopolitical evidence may be selective **context for U.S. equity decisions** when useful, fresh, lawful and material. U.S.-listed foreign-origin companies remain eligible when the listing/reliability rules pass.

Do not silently broaden actionable processing into foreign-equity product scope simply because context/reference data exists.

## CONT-002 — U.S.-Primary Economic Calendar / Event Semantics

Economic Calendar remains part of canonical Event Intelligence / Macro ownership, not a second calendar engine.

Preserve semantics equivalent to:

- **US_MARKET_CRITICAL** — material U.S. event capable of affecting U.S. readiness/Event Mode;
- **US_CONTEXT** — useful U.S. context, not independently critical;
- **GLOBAL_CONTEXT** — foreign/global evidence relevant to U.S. decisions.

A foreign event does not automatically trigger full U.S. market-critical behavior. Materiality, relevance, timing and actual impact govern escalation.

## CONT-003 — Community Intelligence / Global Evidence Fusion Hub

Preserve one canonical source-agnostic **Global Evidence Fusion Hub**, not separate social-feed products.

Canonical flow:

**source → rights/AI eligibility → normalize → U.S. ticker/entity resolution → dedupe/repost cluster → spam/noise filtering → mention velocity/source diversity/narrative change → authoritative corroboration → materiality/confidence → canonical evidence event → authorized consumers**

Potential adapters include permitted/official/user-authorized X, Reddit, Discord, Telegram and future sanctioned WhatsApp/equivalent sources.

Community evidence is contextual/untrusted until appropriately corroborated and cannot directly mutate protected deterministic Day/Swing/Long truth.

Telegram/Watcher Guru or similar fast-alert context may be used in private development only within applicable terms. Prefer authoritative resolution/corroboration before durable/AI use. Commercial/hosted readiness requires rights review and restriction/replacement/removal where needed.

## CONT-004 — Unusual Volume & Volatility Intelligence

Preserve this already-established capability inside **Opportunity Radar / Discovery**, not as another scanner.

Applicable evidence includes:
- session/time-of-day-normalized RVOL;
- dollar-volume + spread/liquidity gates;
- range/volatility expansion;
- price dislocation/confirmation;
- persistence across Radar cycles;
- material catalyst/news/event context;
- permitted community evidence only as supporting context;
- provider/data-health truth.

Opportunity/Discovery Score is contextual discovery intelligence, not protected Day/Swing/Long Score and not probability of profit.

## CONT-005 — Historical Replay / Point-in-Time Validation

Historical Replay/Scenario validation remains a real validation/learning capability using canonical evidence and real deterministic engines with strict no-lookahead truth.

It is not paper trading, mock brokerage or execution simulation. ASBI/TDTI/AODR/13F/adaptive evaluation must build on the same point-in-time truth principle.

## CONT-006 — Runtime Priority / Existing Allocation Authority

Preserve the existing allocation/subscription ownership. **Do not create a second subscription manager** merely because later discussion calls it a Dynamic Multi-Feed Subscription Manager.

Canonical runtime priority remains conceptually:

- **Tier 0 — Market Critical:** SPY, QQQ, selected/researched ticker, critical event/readiness truth;
- **Tier 1 — User Actionable:** active watchlists/desks plus approved high-priority tradables `GLD`, `SLV`, `USO`;
- **Tier 2 — Opportunity Radar promoted candidates**;
- **Tier 3 — broad discovery**;
- **Tier 4 — background/history/maintenance**.

Under pressure, lower-value work yields first: **Tier 4 → Tier 3 → optional Tier 2 before Tier 0/1** wherever possible.

Promotion/demotion remains bounded, provider-budget-aware and hysteresis/TTL-aware. Live-priority evolution must reuse/refactor the canonical allocation manager rather than append a competing subscription authority.

# 4. Ownership, Administration, User Lifecycle & Transferability

## CONT-007 — Canonical Ownership Role Model

Preserve:
- exactly **1 active SUPER OWNER** at all times;
- up to **5 active OWNER** accounts in addition;
- ADMIN / USER / DEMO below them.

SUPER OWNER-only irreversible authority includes applicable ownership transfer/sale, OWNER appointment/removal, controlled successor SUPER OWNER transfer and equivalent irreversible ownership actions.

OWNER has full ordinary product/platform governance and proprietary documentation access but cannot independently create/replace/demote SUPER OWNER authority or transfer product ownership.

ADMIN authority is **capability-based**, not inferred from the ADMIN label. Limited ADMIN receives only delegated capabilities; selected/full-capability ADMIN may receive deeper operations only through canonical authorization.

UI, direct routes, APIs, payload redaction and audit evidence must consume the same capability truth.

## CONT-008 — User/Role/Status Lifecycle Preservation

Role/status lifecycle is server-side canonical truth. Disabling/suspending/expiring access must block access and revoke/revalidate active sessions without deleting the user's durable account/settings/watchlist/audit history unless a separately approved retention policy says otherwise.

Reactivation should reuse the existing account rather than manufacture a new identity where safe.

Role/status/capability changes must be append-audited with actor and timestamp. No stale session claim may preserve removed authority.

Any access-request/invitation/duration workflow that is delivered must treat User Management/IdentityService as the source of truth; notification email is never the authorization authority.

## CONT-009 — Transferable Asset Registry / Ownership Transfer Readiness

Maintain a governed **Transferable Asset Registry** covering applicable:
- official system identity/email;
- market-data subscriptions/provider/service accounts;
- API credential ownership metadata without exposing secrets;
- billing ownership;
- recovery/MFA ownership;
- domains/certificates;
- cloud/server/hosting assets;
- source repository/release/signing ownership;
- build/release infrastructure;
- documentation/governance;
- audit/history/provenance;
- data-rights/licensing obligations;
- dependencies/transfer prerequisites.

Registry records ownership/location/process, not secret values. Ownership transfer requires reauthentication, explicit audit evidence, successor validation and appropriate rollback/recovery planning.

# 5. Role-Aware Documentation & AI Retrieval

## CONT-010 — Documentation Classes / RBAC

Preserve role-aware in-product documentation:
- **USER** — sanitized workflow/freshness/readiness/usage docs;
- **DEMO** — limited Quick Start/help;
- **ADMIN** — user docs plus only authorized operational/admin docs;
- **OWNER / SUPER OWNER** — full proprietary developer/product-engineering/governance docs.

Selected ADMIN capabilities may expose deeper operations docs only when backend authorization permits the underlying capability.

Server-side authorization is mandatory; UI hiding alone is not access control.

AI/retrieval inherits the same document/capability authorization. Never retrieve OWNER-only content and rely on prompt suppression afterward.

Canonical documentation should carry useful metadata such as document ID, audience, owner, introduced/last-updated version, related contract, dependencies, status and integrity/hash where appropriate.

Affected builds maintain a Documentation Impact Manifest or equivalent traceability and update only materially affected modules. Stale/role-leaking documentation can fail release qualification.

# 7. Executable Governance Closure

## CONT-012 — Governance Is Executable Product Intent

Every material approved governance item has an implementation disposition:

- **CURRENT_RELEASE_BLOCKER**;
- **CURRENT_RELEASE_PROCESS_HARDENING**;
- **NEXT_RELEASE_MANDATORY_ENTRY**;
- **FUTURE_STRATEGIC**;
- **ALREADY_IMPLEMENTED / INHERITED**;
- **OPEN_DEFECT / RECONCILE**.

`APPROVED` is never a synonym for `IMPLEMENTED`.

## CONT-013 — Required Traceability Chain

Maintain applicable traceability:

**Approved Scope/Contract ID → roadmap/release disposition → G1 item → canonical owner → source implementation → tests/gates → packaged-runtime evidence → Stable disposition → outcome/telemetry → G16 learning**

G10/G12/G14/G16 explicitly detect:
- approved but never scheduled;
- scheduled but never implemented;
- implemented but not integrated;
- integrated but not tested;
- source-tested but not packaged/runtime-proven;
- runtime-proven but ineffective/noisy/low-value;
- useful and worth strengthening;
- redundant/obsolete and safe to consolidate/supersede;
- open defect without closure evidence.

Documentation correctness cannot make contradictory source/runtime PASS.

# 10. Open Defect Carry-Forward — No False Closure

## CONT-024 — Master Market Symbols Control/Layout — OPEN_DEFECT / RECONCILE

Until current source/runtime evidence proves closure:
- preserve Global/Master Registry semantics;
- fix control/layout hierarchy without semantic drift;
- validate responsive geometry and add/remove behavior;
- preserve idempotency/no duplicate membership effects;
- do not close based on an old plan/screenshot alone.

## CONT-025 — Prep `Requires Review` Repetition — OPEN_DEFECT / RECONCILE

Observed risk: Pre-Market/Market Open Prep can show a long repeated per-symbol warning list (for example repeated liquidity-risk cards), burying material exceptions or exaggerating one shared upstream issue.

Required behavior when backend truth is correct:
- surface shared/root cause once where applicable;
- group by reason/severity;
- show counts;
- sort by severity/materiality/actionability;
- bound initial list;
- View All/collapsible drill-down;
- preserve per-symbol detail when expanded;
- dedupe identical reason text;
- never hide genuinely independent material risk.

When a shared stale/degraded dependency is the root cause, ADR-GDI blast-radius/reason semantics should express that cause rather than presenting unrelated symbol failures.

# 14. Audited 10/10 Continuity Quality Scorecard

A reconciliation may be called **10/10** only when all dimensions pass:

1. **Discussion/Approval Coverage** — material approved items in the review window accounted for.
2. **Historical Stable Coverage** — relevant certified inherited capabilities accounted for.
3. **Canonical Ownership** — no duplicate engines/routers/stores/managers introduced.
4. **Roadmap/Release Disposition** — every non-current item has named placement/classification.
5. **Executable Traceability** — requirement → owner → source → test → package/runtime → G16 path exists where applicable.
6. **Defect Continuity** — unresolved user-reported defects remain open until evidence closes them.
7. **Security/Rights/Role Continuity** — RBAC, role-aware sessions, AI retrieval, data rights and ownership-transfer boundaries survive refactors.
8. **Performance/Reliability Continuity** — inherited features remain bounded, provider-efficient, priority-aware and ADR-GDI-compatible.
9. **Delivery/Platform Truth** — required native/hosted targets and actual-artifact proof are explicit; no fabricated platform PASS.
10. **Future-Loss Prevention** — G0/G10/G16/Major Closure detect approved-but-missing, implemented-but-unintegrated and silently dropped behavior.

A score below 10 requires remediation before describing the reconciliation itself as 10/10.

This score evaluates **continuity/governance quality**, not whether future v20 ASBI/TDTI/AODR/ADR-GDI capabilities are already implemented.

# 15. Adaptive Use — Not Shelfware

This contract changes build behavior; it is not a documentation trophy.

Future plans and gates must actively consume it. G16 measures whether governed capabilities are useful, reliable, efficient and understandable, then applies:

**preserve what works → strengthen decision value → consolidate duplication → fix failure modes → retire low-value/redundant behavior with evidence → feed the next adaptive plan**.

DE.PULSE should become simpler to use while becoming more capable internally. Governance exists to make that evolution cumulative, safe, testable and difficult to forget.
